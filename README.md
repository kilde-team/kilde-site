# kilde-site

The website for [**kilde**](https://github.com/kilde-team/kilde), a screen and audio
recorder for macOS — the menu bar app is open source (MIT), built on the local
recording engine.

A hand-written static site (no build step, no framework, and no application
JavaScript — the single script is the cookieless GA4 bootstrap in
`public/assets/analytics.js`, see [Measurement](#measurement-ga4)), deployed to
Cloudflare with [Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/).

```
                   # build is Japanese-only, but en/zh-Hans/ko/es
                   # localization has landed in the kilde repository (#138)
    demo/
      kilde-demo-60s-{ja,en}.mp4
                   # the 60-second demo on the top pages (issue #1),
                   # generated by the kilde repository's video pipeline
                   # (docs/appstore/tools/video.py, kilde#399) — regenerate
                   # there, never re-encode here
      poster-{ja,en}.jpg
                   # the <video> poster; with preload="none" this is the only
                   # byte fetched until the visitor presses play
      appstore/kilde-demo-appstore-{ja,en}.mp4
                   # 30-second App Store preview cuts (1920x1080, H.264+AAC),
                   # kept here as the durable home until they are uploaded to
                   # App Store Connect with the next editable version —
                   # not linked from any page

.github/workflows/deploy.yml
```

There is no templating: each page carries its own header and footer. When you change the
navigation or the footer, change it in all eighteen pages (the two legal pages have a
minimal footer — the navigation is the part that must stay in sync everywhere). The five
search landing pages are deliberately kept out of the navigation; their header and footer
still mirror the site's, so include them when the shared chrome changes.

## Keeping the comparison page current

`/compare/` and `/ja/compare/` state other vendors' prices and features with links to
their official pages and a confirmation date. That page is only honest while the facts
are fresh, so re-check it **every six months (in April and October)**:

1. Open every link in the pages' "Sources" section (they are the vendors' official pages).
2. Check each table cell against what the vendor's page says. Prices drift the most;
   feature claims must stay describable from the vendor's own words — never from review
   sites or assumptions.
3. Move the confirmation date (the `updated` chip, the "Confirmed" spans, and the
   `<lastmod>` entries in `public/sitemap.xml`) to the day you re-checked — **even when
   nothing changed**, the date is what records that the page was re-verified. Update the
   cells themselves only where a fact changed, and note what changed in the pull request.
4. Ship through a pull request as usual.

If a vendor disappears or a source link rots, drop that row/column instead of leaving an
unverifiable claim on the page.

## Local preview

```sh
npm install
npm run dev        # wrangler dev — serves public/ with the same routing as production
```

Or, without any dependencies:

```sh
python3 -m http.server -d public 8787
```

Note that `python3 -m http.server` does not apply `_headers`, the `/privacy` →
`/privacy/index.html` rewrite, or the custom 404 page. `wrangler dev` does.

## Deploying

```sh
npx wrangler login
npm run deploy
```

CI deploys on every push to `main` via `.github/workflows/deploy.yml`. It needs two
repository secrets:

| Secret | Where to get it |
|---|---|
| `CLOUDFLARE_API_TOKEN` | Cloudflare dashboard → My Profile → API Tokens → *Edit Cloudflare Workers* template |
| `CLOUDFLARE_ACCOUNT_ID` | Cloudflare dashboard → Workers & Pages → Account ID |

### Custom domain

The site's canonical URLs assume `https://kilde.site/`. After the first deploy, attach the
domain in **Workers & Pages → kilde-site → Settings → Domains & Routes**. If a different
domain is used, update the `canonical`, `hreflang`, `og:url` and `og:image` values in all
eighteen HTML pages (top, comparison, five landing pages and legal, each EN and JA), plus
`robots.txt` and `sitemap.xml`.

## Measurement (GA4)

Pages load `public/assets/analytics.js`, a cookieless Google Analytics 4 bootstrap.
It reports to the GA4 property **kilde-a1ae7** (555463514) — the same property the
menu bar app reports to via Firebase, so web and app data live side by side. The
`GA_MEASUREMENT_ID` in the file (`G-0SRWK1ZCSC`) is the site's Google tag, which
carries the web stream *kilde-site* (stream 16109385729) as a destination: one load
feeds both that stream and the stream of the same name in the old "kilde" property
(554727401, harmless duplicate). Do NOT switch the constant to the stream's own
measurement ID — that tag does not initialize when loaded directly (verified
2026-10-12, issue #11) and measurement stops silently. Consent Mode denies
`analytics_storage`, so no cookies or localStorage are written; visitors sending
Do Not Track / Global Privacy Control are skipped entirely. The
[privacy policy](public/privacy/index.html) documents this setup — keep the two in
sync when touching `analytics.js`.

### Campaign URLs (UTM)

Any URL we publish elsewhere gets UTM parameters so GA4 separates it from Direct
traffic (kilde-site#12):

- `utm_source` — where the link lives: `producthunt`, `x`, `reddit`, `hackernews`, `blog`, `release-notes`, …
- `utm_medium` — kind of placement: `social`, `referral`, `announcement`, `email`
- `utm_campaign` — the initiative, kebab-case: `ph-launch-2026q4`, `v0.12-release`

Example: `https://kilde.site/?utm_source=x&utm_medium=social&utm_campaign=v0.12-release`

### Reading store clicks

The Mac App Store buttons are outbound links, so GA4's enhanced measurement records
them automatically as `click` events (`outbound = true`, `link_url` containing
`apps.apple.com`). App Store links themselves cannot carry UTM parameters (Apple
strips them), so the click event is the measurement of the site → store step. In
GA4 look at Reports → Engagement → Events → `click`, filtered on `link_url`.
